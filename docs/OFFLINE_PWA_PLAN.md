# Офлайн PWA как единая база для web / TWA / iOS

Статус: план + модель сосуществования онлайн/офлайн согласованы (2026-09-10), к реализации не
приступали (2026-09-09).

## Зачем это

Задача: сайт и максимум платформ минимальными усилиями, обязательно офлайн на Android и iOS,
без нативного кода кроме шорткатов и Share API.

Аудит показал, что исходная постановка описывает работу, которая **уже сделана** в `dg-app-full`:

1. Приложение работает **не** на нативном Capacitor SQLite, а на `@sqlite.org/sqlite-wasm` 3.53
   (`package.json:24`) в module-worker'е (`src/db-worker.js`), база в OPFS через
   `installOpfsSAHPoolVfs` (`db-worker.js:101-109`, SAH-pool выбран именно потому, что COOP/COEP
   на сайте нет). То есть "перевести адаптер с Capacitor-плагина на Wasm" стоит 0 дней.
2. Прослойка это не реимплементация API: `src/app.js` подменяет `window.fetch` и зовёт
   **тот же** `dg-node/core/search-core.js`, собранный `build-core-bundle.js`. Совместимость
   `/search` по построению, плюс `test/core-parity.mjs` и `test/e2e-browser.js` диффят 24 ответа
   против снимков живого сайта.
3. Кастомных C-расширений и токенизаторов нет. Единственная нестандартная вещь это JS-функция
   `regexp_test` (`core/search-core.js:290-295`), уже проброшенная в Wasm через `nodeSqliteShim`
   (`db-worker.js:57-70`). FTS5 `trigram remove_diacritics 1` требует SQLite >= 3.45, в
   wasm-сборке 3.53 есть. `bm25/snippet/highlight/ICU/collations` не используются, `dbstat`
   только на этапе сборки базы.
4. **Сжатие бесполезно и не нужно.** 600 МБ это все языки SC; 170 МБ это языковой срез ru+en
   (`build-app-db.js`), а не результат компрессии. Триграммный индекс высокоэнтропийный:
   замерено `gzip 168MB -> 177MB` (`src/offline-status.js:280-287`), то есть больше исходного.
   Никакого `DecompressionStream` не требуется. Стриминг уже правильный:
   `pool.importDb(name, callback)` пишет базу в OPFS чанками из `response.body.getReader()`
   (`db-worker.js:72-97`), в память 170 МБ не попадают.
5. Ничего на сайте не обходит fetch-шим: DataTables client-side, autocomplete из localStorage,
   единственная `<form>` с `preventDefault()`. XHR/`$.ajax`/EventSource нет.

Значит настоящая работа не "перенести поиск на клиент", а **вернуть уже готовый офлайн-слой из
приложения обратно в сайт**, чтобы PWA был автономен сам по себе, а обёртки стали тонкими.

## Решения (согласованы)

- Офлайн-слой переезжает в `dg-node`. Сайт становится самодостаточным офлайн-PWA "под ключ".
  `dg-app-full` и `dg-twa` остаются маленькими репозиториями-обёртками и не содержат
  копии офлайн-логики (иначе она разъедется, ровно как разъезжался `mobile/www` до выноса).
- Скачивание базы: **opt-in кнопкой** в настройках. До нажатия сайт работает как сейчас,
  через сервер; шим не перехватывает ничего.
- iOS: сначала PWA (нативного кода ноль), Capacitor iOS отдельным этапом позже.
- Обновление уже установленной библиотеки: **только уведомление + кнопка**. Раз в запуск дешёвая
  сверка с `db-manifest.json`, скачивание — по явному согласию тем же путём, что и первое.
  Фонового автоскачивания 170 МБ нет.
- Первое скачивание **не блокирует данные**: пока база качается/открывается, поиск и ридер
  работают через сервер, как сейчас.
- Область работ на этом шаге — **только сайт (`dg-node`)**. `dg-app-full` не трогаем: он
  подтянет офлайн-слой из dg-node отдельным шагом (Этап 2).

## Два офлайна: как сосуществуют онлайн-PWA и офлайн-PWA (2026-09-10)

«PWA онлайн» (уже есть: `configs/manifest.json` + `public/service-worker.js`) и «PWA офлайн» —
не два режима одного переключателя, а два независимых слоя:

| Слой | Что даёт | Когда работает | Кто отвечает |
|---|---|---|---|
| **A. Оболочка** | сайт открывается, навигация и pushState-URL живут без сети | всегда, без спроса | Service Worker (после Этапа 1: precache + navigation fallback) |
| **B. Данные** | `/search`, `/search/*`, `/search/enrich`, `/api/text/*`, `/api/nav/*` отвечают без сети | opt-in: база реально есть в OPFS | fetch-шим + `core/search-core.js` в воркере + SQLite в OPFS |

Ключевое: состояние определяется **не «режимом PWA», а наличием базы в OPFS** — одна проверка
`op: 'status'` в воркере при старте. Ничего больше переключать не нужно.

### Состояния

1. **Базы нет** — шим не устанавливается вообще, `window.fetch` не обёрнут. Ровно сегодняшний
   сайт; скачивание само не начинается (только кнопка в настройках).
2. **Идёт первая загрузка** — шим уже стоит, база ещё не открыта. Data-запросы идут на сервер.
   *Правка относительно `dg-app-full`/`src/app.js`*: там все data-роуты делают `await ready`, то
   есть поиск ждёт окончания 170 МБ (в приложении иначе нельзя — оно обязано быть офлайн). На
   сайте так нельзя: ожидание только когда база уже есть.
3. **База есть + сеть есть** — данные из локальной базы (local-first), сервер для data-роутов не
   дёргается. Раз в запуск — сверка с `db-manifest.json`; она только **сообщает**, обновление
   скачивает читатель кнопкой.
4. **База есть + сети нет** — поиск и ридер из базы, оболочка из SW-кеша. Полный офлайн.
5. **База вытеснена / побита / не той схемы** — при старте не найдена → шим не активируется →
   сайт сам возвращается в состояние 1, без «сломанного» промежуточного режима. Если сети тоже
   нет — явный сценарий «библиотека пропала, скачать заново» (Этап 4 для iOS, где вытеснение
   вероятнее всего).

### Правила, чтобы слои не конфликтовали

- **Атомарность.** Шим владеет либо всеми data-роутами, либо ни одним. Смешанный ответ (поиск из
  базы, ридер с сервера или наоборот) покажет сегменты, которых вторая половина не отрисует.
- **Local-first, а не network-first.** При наличии базы ответ всегда локальный: это и есть
  условие паритета, который диффят `test/core-parity.mjs` и `test/e2e-browser.js`. Свежесть
  решается манифестом, а не тем, повезло ли с сетью; иначе один запрос в одном сеансе даёт два
  разных ответа.
- **Библиотека — срез, а не сервер.** 170 МБ = ru+en. Всё, чего в срезе нет, честно уходит на
  сервер, если сеть есть: языки вне среза (`langNeedsOnline` в `src/app.js`) и транслитерация
  (`/api/transliterate`, локальный `script-engine` vs сервер). Без сети — явное сообщение
  «нужен интернет: этого языка/системы письма нет в офлайн-библиотеке», а не пустая выдача.
- **SW и шим не пересекаются.** Ответы шима вообще не уходят в сеть, поэтому SW их не видит и не
  кеширует — в кеше SW только оболочка (`index.html`, бандлы, css, шрифты, `core-bundle.js`,
  wasm). 170 МБ живут в OPFS, а не в Cache API.
- **Один origin на всё.** Вкладка, установленное PWA и TWA делят один OPFS, один SW и один
  `localStorage`. Отсюда два обязательных механизма: замок на скачивание (две вкладки не должны
  тянуть 170 МБ параллельно) и handshake по `build_id` — после обновления базы у других вкладок
  открыта старая, им нужно сказать «обнови страницу».
- **Согласие и обратимость.** До согласия — ноль перехвата; отказ ничего не меняет; «удалить
  библиотеку» возвращает состояние 1 без переустановки сайта.

## План

### Этап 1. Офлайн-слой в dg-node (основная работа)

Новое в `dg-node`:

- `public/offline/` : `app.js` (fetch-шим), `db-worker.js`, `offline-status.js`,
  `offline-library-settings.js`, `vendor/sqlite-wasm/*` (переезжают из `dg-app-full/src/`).
- `public/offline/platform.js` : всё платформенное, что сейчас вкраплено в `app.js`, вынести
  за один интерфейс `{ askConsent, download }`:
  - браузерная реализация по умолчанию (стрим прямо в OPFS, согласие обычным диалогом);
  - Capacitor-реализация (`Network`, `DgDownloader`, `convertFileSrc`) остаётся в `dg-app-full`
    и подставляется через `window.dgPlatform` до загрузки `app.js`.
  Затрагиваемые места: `app.js:100-116` (Network), `:125-208` (DgDownloader), `db-worker.js:77`
  (`_capacitor_file_` sniff).
- `build-core-bundle.js` переезжает в `dg-node` (`npm run build-core-bundle`), выдаёт
  `public/offline/core-bundle.js`. `dg-app-full` забирает готовый файл вместо своей сборки.
- Активация шима: только если база реально есть в OPFS (`op: 'status'`) или пользователь нажал
  "скачать". Иначе `window.fetch` не трогаем вообще.
- Перенос `app.js` — не копия: `await ready` в data-роутах остаётся только когда база уже
  открыта, во время первой загрузки запросы идут на сервер (см. «Состояния», п.2). Плюс замок на
  скачивание и handshake по `build_id` — в приложении не нужны (один экземпляр, один процесс), в
  браузере обязательны (вкладка + установленное PWA + TWA на одном origin).

Правки в `dg-node`:

- `search/index.html` : добавить маркер `<!-- dg:app-scripts -->` в `<head>` и грузить
  `/offline/app.js` первым скриптом. Это же снимает хрупкость `build-page.js`
  (`dropServiceWorker`/`injectAppScripts` больше не должны угадывать структуру `<head>`).
- `public/service-worker.js` : сейчас network-first без precache, офлайн держится на случайно
  закешированном. Нужно: precache оболочки (index.html, `settings-bundle.js`/`home-bundle.js`,
  css, шрифты, `core-bundle.js`, `db-worker.js`, sqlite wasm), **navigation fallback на
  index.html** (без него pushState-URL вида `/dn22:2.2` офлайн отдаёт 404), сохранить
  network-first для остального, имя кеша по build-хешу. Комментарий про легаси cache-first
  оставить, ловушку не воспроизводить.
- `configs/manifest.json` : уже содержит `share_target` и 6 шорткатов, менять нечего.
- `dg-fastify.js` : сделать раздачу `/mobile-data` штатной (сейчас это только прод-симлинк,
  в чекауте отсутствует), проверить `Accept-Ranges` на `.db` (нужен для докачки; у
  `@fastify/static` включён по умолчанию, у самодельного `sendFile` нет), не сжимать `.db`
  (сейчас и так не сжимается: octet-stream не в compressible-наборе).
- Докачка по Range в браузерном пути: сейчас обрыв сети означает рестарт 170 МБ. В APK это
  закрывает Android DownloadManager, в вебе и TWA закрывать нечем, поэтому это часть MVP,
  а не улучшение.

### Этап 2. dg-app-full худеет

- `build-assets.js`/`build-page.js` перестают копировать офлайн-слой из `src/`, берут его из
  чекаута dg-node вместе с остальным UI. В `src/` остаются `native-bridge.js` и
  Capacitor-реализация `platform.js`.
- Вырезание регистрации SW в WebView оставить как есть.
- `DG_NODE_REF` продолжает пинить версию сайта.

### Этап 3. TWA

- Кода не требуется: TWA открывает тот же origin, шим и SW приезжают с сайта.
- Проверить на устройстве: `navigator.storage.persist()`, что Chrome не вымывает 170 МБ,
  и что сворачивание приложения во время скачивания не убивает загрузку (страховка это Range-докачка
  из этапа 1).
- Шорткаты и Share Target в `twa-manifest.json` и `configs/manifest.json` уже есть.

### Этап 4. iOS PWA

- Проверка на живом устройстве (Safari 17+): OPFS SAH-pool, квота под 170 МБ, поведение
  установленного на Home Screen PWA при нехватке диска.
- UI-ветка "библиотека пропала, скачать заново" (`offline-status.js` уже умеет сообщать об
  ошибке, нужен явный сценарий потери базы).
- Осознанные ограничения WebKit: нет Web Share Target и App Shortcuts. Это и есть причина
  будущего этапа 5.

### Этап 5 (позже, отдельным решением). iOS native

`npx cap add ios` поверх того же `www`, Share Extension и шорткаты, фоновая загрузка на
`URLSession` вместо Android DownloadManager.

- Ручной чеклист: opt-in скачивание с прогрессом, обрыв сети и докачка, поиск и ридер в

- Отдельно — матрица состояний из раздела «Два офлайна», каждое проверяется вручную (автотесты

## Этап 1: что сделано (2026-09-10)

Реализовано и проверено вживую на этом чекауте (`/var/www/html/dg-node-test`, ветка `front`).

**Новые файлы**

- `build-offline.js` (`npm run build-offline`) — копирует вендор sqlite-wasm из `node_modules`,
  собирает `public/offline/core-bundle.js` из `core/search-core.js` и пишет
  `public/offline/build-id.json` (хеш офлайн-слоя; им версионируется кеш service worker'а).
  generated-артефакты в git не попадают (`.gitignore`).
- `public/offline/platform.js` — браузерная реализация `{ distBase, askConsent }`; нативная
  сборка подставляет свой `window.dgPlatform` до загрузки `app.js`.
- `public/offline/app.js` — fetch-шим сайта. Отличия от `dg-app-full/src/app.js` перечислены в
  его заголовке: гейт по наличию базы, нет `await ready` на data-роутах, same-origin вместо
  форварда на `dhamma.gift`, выборы «одного владельца» через Web Locks (SAH-пул однописательный,
  вторая вкладка остаётся на сервере), нет локального движка скриптов.
- `public/offline/db-worker.js` — воркер (OPFS + sqlite-wasm). Портирован оттуда же, плюс:
  `open({download:false})` для стартового зонда, дешёвая проверка наличия базы без загрузки
  wasm, `delete`-операция, **докачка по `Range`** (scratch-файл `dg-mobile.<build>.partial`),
  проверка квоты до скачивания и `PRAGMA quick_check` после.
- `public/offline/offline-status.js` — порт UI-скрипта (прогресс, ошибки, апдейт).
- `public/offline/offline-library-settings.js` — строка в настройках.
- `test/offline-e2e.js` — сквозной тест: состояние 1 (нет перехвата) → опт-ин скачивание →
  паритет против **того же ядра над `dg.db`** → офлайн-перезагрузка pushState-URL.

**Правки**

- `search/index.html` — маркер `<!-- dg:app-scripts -->` и три тега `/offline/*.js` первыми в
  `<head>` (шим обязан быть установлен раньше любого другого скрипта).
- `settings/index.html` — строка «Офлайн-библиотека» (id `dgOfflineLib*`) + тег скрипта.
- `public/service-worker.js` — precache оболочки (best-effort, по одному URL), navigation
  fallback на `/`, имя кеша `dg-shell-<build-id>`, самоочистка старых кешей; `/mobile-data/*` и
  любые `Range`-запросы не трогает вовсе.
- `dg-light.js` / `dg-fastify.js` — маунт `/offline` (no-cache + ETag) и явный `/mobile-data`
  (`Accept-Ranges`, 206, без gzip/br, `max-age=3600`, тихий 404 при отсутствующем каталоге).
- `package.json`, `.gitignore`.

**Измерено (меняет цифры плана)**

- Срез `--langs=ru,en` из текущего `dg.db` — **479.3 МБ** (data 194.5 · indexes 97.5 · fts 186.8),
  сборка ~157 с; в плане фигурировали 170 МБ. Это и трафик, и квота, и время установки.
- Скачивание 479 МБ с локального сервера в OPFS + импорт + `quick_check` — ~90 с (Chromium,
  headless, постоянный профиль).
- В браузере на этом срезе: поиск/ридер/навигация отвечают локально; офлайн-перезагрузка
  `/dn22:2.2` → 200, ридер отдаёт 454 сегмента.

**Найденное по ходу (важно для эксплуатации)**

1. `importDb()` у sqlite-wasm не проверяет результат записи: при нехватке места Chrome отвечает
   отрицательным числом, пул считает «намеченные» байты — и на выходе база с дырами. Отсюда
   проверка квоты до и `quick_check` после; без них симптом — `SQLITE_CORRUPT` после 479 МБ.
2. `navigator.storage.estimate()` в анонимном профиле Chromium показывает 1 ГиБ, но записи в OPFS
   падают уже после ~230 МБ (FILE_ERROR_NO_SPACE). Любой тест офлайн-слоя обязан работать на
   постоянном профиле (`launchPersistentContext`); на реальном браузере квота измерялась как 10 ГиБ.
3. `/mobile-data/*.db` отдавался с `Content-Encoding: gzip|br` в обоих серверах (mime-db считает
   `application/octet-stream` сжимаемым) — для 206 это ещё и неверно. Отключено пер-роутно.
4. Паритет проверяется против **`dg-fastify.js`** (боевой сервер: `core/search-core.js` + `dg.db`) и
   против того же ядра над `dg.db`; расхождение с любым из них — провал теста. Grep-путь
   `/search` остался только в `dg-light.js`, который в бою не используется: он и разошёлся с

   `dg-light.js` когда-нибудь понадобится, его поиск надо переводить на ядро так же, как это
   сделано в `dg-fastify.js`.
5. `/api/text` у `dg-fastify.js` отдаёт `availableLangs` (языки, в которых у сутты есть перевод) —
   офлайн-воркер теперь тоже, но по своему срезу: `en,ru` против `ru,sr,de,en` у сервера. Тест
   проверяет это поле как **подмножество** серверного, остальное — строго.

**Тесты**

| Команда | Что проверяет |
|---|---|
| `npm run test-offline-parity` | бандл (`public/offline/core-bundle.js`) отвечает как исходное `core/search-core.js` на том же `dg.db` — 14/14 (локальный аналог `test-parity` из `dg-app-full`) |
| `npm run test-offline-resume` | обрыв загрузки: первый ответ приходит «успешно», но короче манифеста — вторая попытка обязана уйти с `Range: bytes=<на диске>-` и база обязана открыться (проверено: `bytes=20171980-`, 206, `nav` отвечает) |
| `npm run test-offline` | полный цикл в Chrome: нет библиотеки → опт-ин скачивание 479 МБ → паритет 22/22 против `dg.db` и 22/22 против `dg-fastify.js` → офлайн-перезагрузка pushState-URL |

Серверная раздача проверена на реальном файле 479 МБ: `Accept-Ranges: bytes`,
`Cache-Control: public, max-age=3600`, **без** `Content-Encoding` даже при
`Accept-Encoding: gzip, br`; `Range: bytes=100-199` → 206 `Content-Range: bytes 100-199/502530048`;
`Range: bytes=500000000-` (докачка) → 206 на 2 530 048 байт.

Отдельно стоит знать: Chrome сам переигрывает идемпотентный GET, оборванный на середине тела
(в тесте сервер видел два запроса, а воркер — один), поэтому обрыв для проверки докачки
смоделирован укороченным `Content-Length` — это и более злой случай, ровно тот, что описан в
`db-worker.js`: поток заканчивается чистым `done`, без ошибки и без стойла.
