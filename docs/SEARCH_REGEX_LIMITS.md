## 2. Что сделано по #1

Числа — в `configs/search/regex-limits.json`, ни одного в коде. Правки требуют рестарта.

```jsonc
{
  "enabled": true,
  "minLiteralChars": 3,      // в шаблоне обязана быть обычная цепочка букв/цифр, как "duk"
  "maxPatternLength": 128,
  "timeoutMs": 20000,        // 20 с: dhamm.* считается 4-8 с, запас ~2.4x
  "maxConcurrent": 1,        // 3.8 ГБ RAM, prod уже ~0.9 ГБ, пик одного широкого поиска ~0.5 ГБ
  "maxRows": 80000,          // dhamm.* = 55k строк; шире — ответ частичный + truncated: true
  "prefilter": true,         // литералы шаблона -> FTS-отбор вместо скана всего корпуса
  "rateLimit": { "trustProxy": ["127.0.0.1", "192.168.1.18"], "windowMs": 60000, "max": 10,
                 "maxTrackedIps": 10000 }
}
```

- `core/regex-worker.js` + `core/regex-runner.js` — шаблонный поиск выполняется в отдельном потоке,
  который по `timeoutMs` **убивается** (`worker.terminate()` прерывает застрявший regex — проверено:
  воркер, застрявший в `(.+)+#`, убивается за ~5 мс, главный поток продолжает обслуживать). После
  убийства воркер поднимается заново. Воркер открывает `dg.db` сам и поднимает скелет тем же
  запросом, что и `dg-fastify.js`, так что второй реализации поиска нет.
- Гард `regexProblem()`: нет литерала из `minLiteralChars` символов (`a.*`, `d.*`, `.*x.*`,
  `(.+)+#`) → 400 с объяснением. Это тот же смысл, что `MIN_KEYWORD_LENGTH` у обычного поиска.
- `regexPrefilterLiterals()`: обязательный литерал каждой альтернативы (`duk.*` → `duk`,
  `kacchap.*|migal.*` → оба) уходит в FTS как `"duk" OR "kacchap"` — скан 1.31M строк заменён
  отбором кандидатов. Если литерал доказать нельзя (`(duk)?x`, `\d{3}duk`) — просто скан в воркере.
- Ответы: 400 (плохой шаблон), 429 (слот занят или лимит на адрес), 503 (таймаут). В `metadata.regex`
  едет `{pattern, literals, scanned, truncated, timedOut}`.
- `core/mcp-server.js` — инструмент `search` ходит тем же путём.
- Лимит на адрес считается по реальному клиенту: `trustProxy` в конфиге — **список адресов прокси**
  (apache `127.0.0.1`, nginx `192.168.1.18`), не `true`/число хопов, иначе `X-Forwarded-For`
  подделывается. Если nginx не пробрасывает адрес клиента — все попадут в один бакет; видно по
  строке `[regex] rate limit hit by <адрес>` в `pm2 logs test`.

Измерения (HTTP, `?fast=1`):

| запрос | было | стало |
|---|---|---|
| `a.*`, `d.*` | 11–15 с, ~1 ГБ, сайт стоит | 400 за 2 мс |
| `duk.*` | скан 1.31M строк | 200 за 1.4 с, прочитано 16 254 |
| `dhamm.*` | скан 1.31M | 200 за 4.3 с, 2332 сутты |
| `the.*` | 1.9 с / 346 МБ и без границы | 200 за 1.9 с, 80 000 строк, `truncated: true` |
| `duk(.+)+#` | не возвращался, сайт вставал | 503 через 20 с, поток убит |
| 11-й шаблон/мин с адреса | без лимита | 429 |

## 3. UI: плашка обрезки и обогащение

- **Плашка «вывод обрезан»** (`search/index.html` + `.rh-regex-limited` в `search/css/home.css`,
  строки `results.regexTruncated` в `configs/search/lang_{ru,en}.json`). Показывается только когда
  сервер сам пометил `metadata.regex.truncated` — то есть только у шаблонного поиска; у обычного
  `?q=the` ни флага, ни обрезки нет, и плашки там не будет.
- **Обогащение цитат** (`/search/enrich`): видимая страница уходит отдельным первым запросом, дальше
  чанки идут по расстоянию от неё (следующая страница, предыдущая, через одну…), чанк 250 id,
  4 запроса параллельно (`ENRICH_CHUNK_SIZE`, `ENRICH_PARALLEL` в `search/index.html`).
  После каждого чанка: `__enriched = true` на объекте строки + `invalidate()` кэша DataTables;
  `draw()` — **только если чанк задел видимую строку** и не чаще раза на кадр
  (`refreshEnriched` / `invalidateEnriched` в `public/overrides/js/search-render.js`). Раньше
  таблица пересобиралась на каждый чанк (`clear()+rows.add()+draw()`), отсюда мелькание.
  Замер на `duk` (6 чанков) и `the` (18 чанков): 3 перерисовки `#pali` за всё фоновое обогащение
  вместо одной на чанк; дальняя страница — 0 заглушек; фильтр находит слово, которое есть только
  в цитате дальней страницы (`dukkaraṁ` → 18 строк, `Dvidhāpathasutta` → 1 из 3994) — то есть
  инвалидация без draw фильтру достаточна.

## 4. Как проверить

```bash
cd /var/www/dg-node-test
node test/regex-guard.js            # 16 проверок: гард, отбор, таймаут, отзывчивость, переспавн

curl -s "http://test.dhamma.gift/search?q=a.*&fast=1"                 # 400
curl -s "http://test.dhamma.gift/search?q=duk.*&fast=1"               # 200, metadata.regex
curl -s "http://test.dhamma.gift/search?q=dhamm.*&fast=1"             # 200, 4-8 с
curl -s "http://test.dhamma.gift/search?q=duk(.%2B)%2B%23&fast=1"     # 503 через ~20 с
```

В браузере: `https://test.dhamma.gift/the.*` (плашка), `https://test.dhamma.gift/duk` (походить по
страницам, потыкать фильтр). Учесть лимит 10 шаблонных запросов в минуту с адреса — 429 это он.

Регрессия после правок: 9 нешаблонных запросов (`fast`, полный на 1.3 МБ, `/search/enrich`,
`/api/text/dn1`, `/api/nav`, `/api/toc`, диакритика, немецкий) — байт-в-байт как до правок;
`test/{query-guard,suggest-words,punct-search}.js` зелёные.
