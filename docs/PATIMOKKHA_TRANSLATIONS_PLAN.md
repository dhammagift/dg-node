# Патимоккха: показать настоящие переводы (Brahmali/Jayasaro), не только пали

Не сделано — план, не код. Владелец нашёл на реальном сервере (`find ... -name
"*pli-tv-bu-pm*"`/`*pli-tv-bi-pm*"`), что переводы Патимоккхи ФИЗИЧЕСКИ есть:

```
en/brahmali/vinaya/pli-tv-bu-pm_translation-en-brahmali.json   — полный перевод
th/jayasaro/vinaya/pli-tv-bu-pm_translation-th-jayasaro.json   — полный перевод
lo/jayasaro/vinaya/pli-tv-bu-pm_translation-lo-jayasaro.json   — полный перевод
en/sujato/name/vinaya/pli-tv-bu-pm-name_translation-en-sujato.json — только НАЗВАНИЯ правил
de/site/name/...-name_translation-de-site.json                — служебный (UI), не перевод
de/blurb/...-blurbs_translation-de.json, pt/blurb/...          — краткие пояснения, не полный текст
```
(то же самое зеркально для `pli-tv-bi-pm`, Bhikkhunī). Реальных ПОЛНЫХ переводов три:
en/brahmali, th/jayasaro, lo/jayasaro. Ни одного русского.

## 1. Что сейчас на самом деле показывается

Проверил `reader/bu-pm-fragment.html`/`bi-pm-fragment.html` (то, что реально отдаёт
`/api/patimokkha-fragment/:side`, `dg-fastify.js`) — текст **чисто пали**, ни слова перевода
ни на одном языке, никакой привязки к переводчику вообще. Источник — НЕ Bilara JSON, а
legacy-страница `assets/texts/{bupm,bipm}.php` (старый сайт), сконвертированная ОДНОКРАТНО
скриптом `convert-patimokkha.js` в статический HTML (`reader/{bu-pm,bi-pm}.html` — полная
страница, и `-fragment.html` — то же самое без обвязки, для инлайн-показа в `/toc`). Файл
`convert-patimokkha.js` переписывает только ссылки на правила (легаси `?q=...#...` →
`/pli-tv-...`), содержимого не трогает и не читает Bilara JSON вообще.

Значит: сегодня Патимоккха в `/toc` и на `/pm.php`/`/bipm.php` — это НЕ "перевод одного
переводчика по умолчанию", а вообще без перевода, просто пали-текст литургии. Реальные
переводы (Brahmali/Jayasaro) лежат на диске, но нигде на сайте не подключены.

## 2. Уже сделано в этой сессии (не относится к пункту 3 ниже)

Первая попытка (скрывать Патимоккху под любым активным непустым фильтром переводчиков) была
отклонена владельцем: "но нужно и показывать их по умолчанию. это важная часть toc". Общий
тоггл "показывать тексты без перевода" обсудили и тоже отклонили — по умолчанию включённый, он
сломал бы фильтр для ОБЫЧНЫХ сутт, не только для Патимоккхи.

Итоговое решение: `public/spa/toc.js` — Патимоккха больше НЕ участвует в переводческом фильтре
вообще (ни скрытии, ни показе по совпадению — `refreshFilterEffects()` просто пропускает
`singlePage`-записи). Вместо этого — отдельный, независимый тоггл "Показывать Патимоккху" в
самом низу панели фильтра, под списками переводчиков (`renderFilterPanel()`), по умолчанию
ВКЛЮЧЁН (`localStorage.dhammaShowPatimokkha`, unset === true). Его состояние применяет
`applyPatimokkhaVisibility()` — вызывается и из `refreshFilterEffects()` (обе ветки), и сразу
при первой отрисовке дерева (когда фильтр переводчиков ещё не тронут). Это не отменяет план
ниже (реальный перевод Brahmali/Jayasaro), просто временное, явное и предсказуемое поведение
для видимости, пока перевод не подключён.

## 3. Как показать настоящий перевод (не сделано)

Нужен НОВЫЙ рендер, не расширение статического конвертера:

1. **Источник данных** — читать `pli-tv-{bu,bi}-pm_translation-{lang}-{translator}.json`
   (Bilara-сегменты, тот же формат, что у обычных сутт) вместо legacy PHP-страницы.
2. **Сегменты и якоря правил** — у Патимоккхи, в отличие от обычной сутты, каждое "правило"
   (пācittiya/pārājika/...) — не отдельный документ, а часть одного большого. Нужно свериться,
   что id сегментов в `pli-tv-bu-pm_root-pli-ms.json` (root) и в `..._translation-en-brahmali.json`
   совпадают 1:1 с уже используемыми `pli-tv-bu-vb-...` ссылками на правила (`ruleIdToUrl()` в
   `convert-patimokkha.js` — та же схема соответствия id может пригодиться, а может и не
   подойти, если сегментация Bilara режет иначе, чем легаси PHP-страница резала якоря).
3. **Эндпоинт**: либо расширить `/api/patimokkha-fragment/:side` параметром
   `?translators=en_brahmali` (по аналогии с `/api/toc/book/:code?langs=`), либо завести новый
   `/api/patimokkha/:side` возвращающий уже собранный HTML/сегменты. Разумнее переиспользовать
   существующий путь рендера сутты (`getFullTextData`/`buildTextDataFromBase`,
   `core/search-core.js`), если Патимоккха физически лежит как обычный `sutta_id` в `texts` —
   тогда это не новый рендерер с нуля, а параметризация уже существующего.
4. **Клиент** (`public/spa/toc.js`, `fetchPatimokkhaFragment`): передавать выбранного в фильтре
   переводчика (когда он один из реальных — brahmali/jayasaro), иначе — как сейчас, чистый пали.
5. **Что НЕ трогать**: `/pm.php`/`/bipm.php` (полная legacy-страница, отдельный прод-маршрут,
   владелец явно просил не трогать легаси без явного запроса) — фикс имеет смысл только для
   инлайн-фрагмента в `/toc`, если владелец не попросит иначе.

## 4. Почему не сделано сейчас

Требует реального корпуса (проверить реальную структуру сегментов `pli-tv-bu-pm_translation-
en-brahmali.json`, сверить с текущей схемой якорей правил) и живого сервера для проверки
рендера — в песочнице нет ни того, ни другого. Кроме того, объём предложения ближе к "новая
фича", чем к однострочному фиксу — сначала стоит решить архитектуру (п.3 выше — переиспользовать
существующий рендер сутты или строить новый) с владельцем, а не гадать реализацию вслепую.
