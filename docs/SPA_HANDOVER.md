# Передача: что сделано на страницах поиска, ридера и настроек (перед сборкой SPA)

Документ для следующего этапа — «склеить поиск и ридер в одну страницу, максимально бесшовно».
Здесь только то, что проверено на живых страницах в этом раунде. Планы и прототип `/spa/`
описаны отдельно — см. `SPA_PLAN.md` и `SPA_INTEGRATION.md`; этот файл про **текущие боевые
страницы**, из которых и придётся собирать SPA.

---

## 1. Что где лежит

| Экран | Файл | Маршрут |
|---|---|---|
| Поиск + результаты | `search/index.html` | `/`, `/{слово}`, `/search/{слово}` |
| Ридер | `reader/reader-template.html` + `reader/megareader.js` | `/{suttaId}`, `/{suttaId}:{segment}` |
| Настройки | `settings/index.html` + `settings/preview-frame.html` (iframe с образцом) | `/settings/` |
| Сервер | `dg-light.js` | всё выше + API |

API, которым живёт поиск:

- `GET /search?q=&scope=&langs=&lb=&la=&fast=1` — быстрый скелет выдачи (числа сразу полные);
- `GET /search/enrich?...&ids=a,b,c` — догрузка цитат и контекста батчами;
- `GET /api/text/:suttaId`, `GET /api/nav/:suttaId` — для ридера.

Маршрут `/:slug` в `dg-light.js` решает, что именно отдать: есть в `skeletonDB` → ридер; нет, но
есть дети главы → заглушка оглавления; нет вообще → страница поиска. Отдельно там же
`findRangeContaining()`: `/an1.9` → 302 на `/an1.1-10:an1.9`, потому что отдельного текста `an1.9`
в корпусе нет, он внутри диапазона.

## 2. Что на странице поиска УЖЕ работает как SPA

Это готовый кусок, его можно брать за основу, а не переписывать:

- **Сабмит без перезагрузки.** `#form submit` → `history.pushState` → `runSearchFromUrl()`.
  Кнопки «назад/вперёд» обрабатываются через `popstate`.
- **`runSearchFromUrl()`** сбрасывает состояние прошлого запроса (`enrichedIds`, `pendingIds`,
  `enrichmentStarted`, `lastSearchJson`, `reportMode`) и заново зовёт `initSearchApp()`, который
  читает ВСЁ из адреса. То есть точка входа «показать выдачу по текущему URL» уже существует.
- **Таблицы стабильны.** `public/overrides/js/search-render.js` инициализирует две таблицы
  (`#pali` по суттам и `#pali-words` по словам) ОДИН раз за сессию страницы; переключение отчётов
  и новые запросы — это `.clear().rows.add().draw(false)`, без `destroy()`. Пересоздавать их
  нельзя: DataTables путается в реестре и портит сортировку (уже наступали).

Чего на странице поиска НЕТ и что придётся добавить для SPA: переход в ридер по-прежнему
настоящая навигация (`window.location.href`) — это осознанно, ридер сейчас другой документ.

## 3. Ридер: что мешает бесшовности

Ридер — отдельная страница со своим набором скриптов, и он завязан на СВОЮ разметку:

- `megareader.js` рисует текст в `#sutta`, читает слаг и сегмент из адреса, сам скроллит к
  сегменту (учитывает `?scroll=instant`: попапу нужен резкий прыжок, новому окну — плавный).
- Для диапазонных текстов id элемента сегмента — ПОЛНЫЙ segment id (`an1.9:1.1`), а не локальная
  часть. В `megareader.js` есть запасной поиск якоря по префиксу — не потеряйте при переносе.
- `smoothScroll.js` восстанавливает позицию чтения и умеет спорить с прыжком на сегмент. Явно
  запрошенный сегмент (хэш ИЛИ `:` в чистом пути) теперь считается приоритетнее восстановленного
  прогресса — иначе переход из поиска уводил мимо найденного места.
- Часть логики ридера живёт в общесайтовых скриптах: `settings.js` (горячие клавиши, ленивая
  загрузка словаря и озвучки), `paliLookup.js` (словарь), `voice.js` (TTS), `openFdg.js`
  (попап-iframe для цитат), `smoothScroll.js`.

**Главный риск при склейке:** все эти скрипты писались под «одна страница = один документ»,
инициализируются один раз при загрузке и читают localStorage тоже один раз. В SPA их придётся
либо переинициализировать на смену вида, либо научить слушать изменения (см. следующий раздел —
там уже есть примеры обоих подходов).

## 4. Ловушки, на которые я наступал (сэкономит время)

Это не теория, каждая стоила отдельной итерации.

**Порядок и специфичность CSS важнее, чем кажется.** Страницы подключают легаси-таблицы стилей
ПОСЛЕ своих инлайновых блоков, и правила с той же специфичностью проигрывают по порядку:
- `extrastyles.css` задаёт `#scrollToTopBtn{bottom:20px;right:20px}` — мой одноимённый селектор
  не работал, помог `body #scrollToTopBtn`;
- `uiextra.css` задаёт `#form.ui-widget #paliauto, #paliauto { padding-left:10px !important }` —
  там ДВА id, поэтому ни `!important`, ни более поздняя позиция не помогали, пришлось уравнять
  число id.

**`z-index` инпута.** У `.searchinput` `z-index: 9`. Иконка внутри поля с меньшим значением
существует, имеет размеры — и не видна, потому что непрозрачное поле рисуется поверх; клик по ней
тоже уходит в поле. Проверять надо не «элемент есть», а `elementFromPoint` по его центру.

**Клик по пали-слову перехватывается дважды.** `settings.js` ловит клик по `.pli-lang/[lang=pi]`
в фазе перехвата, гасит его, лениво догружает `paliLookup.js` и ПЕРЕОТПРАВЛЯЕТ клик заново. Любой
свой обработчик на этих элементах получит событие дважды и без своих меток.

**`openFdg.js` закрывает свой попап по клику мимо него.** Если открыть попап синхронно внутри
обработчика клика, тот же клик дораспространяется и немедленно его закрывает. Лечится
`setTimeout(..., 0)`.

**`paliLookup.js` читает `selectedDict` один раз** при загрузке. Смена режима словаря на лету
требует вызова его же `applyDictConfig(mode)`. Плюс для режимов `dpdfull*/newwindow*` он берёт
язык словаря не из режима, а из глобала `window.isRu` — в чужом контексте (iframe образца) его
надо выставить самому.

**`voice.js` молча выходит**, если на странице нет `a.voice-link[data-slug]` (`if (!slug) return`).
Именно поэтому «Слушать» в поиске сначала не делал ничего.

**Высоту содержимого iframe нельзя мерить через `documentElement.scrollHeight`** — `paliLookup`
вставляет элементы с `position:fixed`, они не в потоке, но в область прокрутки документа входят.
Нужно `body.scrollHeight`.

**Тестовые ловушки (мои же ошибки, чтобы не повторять):**
- `elementFromPoint` и `caretRangeFromPoint` работают ТОЛЬКО по видимой области — элемент за
  пределами экрана даёт `null`, и это легко принять за поломку кода;
- буфер консоли в инструменте не чистится при переходах: старые ошибки выглядят как свежие,
  проверять надо в новой вкладке;
- `getComputedStyle().opacity` сразу после смены класса вернёт стартовое значение анимации, если
  на элементе есть `transition`.

## 5. Состояние: ключи localStorage

Всё общее состояние — в localStorage, отдельного стора нет. Что реально читают эти три страницы:

| Ключ | Смысл |
|---|---|
| `dhammaLanguage`, `siteLanguage` | язык интерфейса |
| `dhammaReaderLangs` | языки чтения (порядок = порядок показа) |
| `dhammaSearchLangs` | языки поиска; при «так же, как для чтения» синхронизируется с предыдущим |
| `dhammaSearchScope` | область поиска (список префиксов); отсутствие ключа = набор по умолчанию |
| `dhammaSearchContextBefore/After` | контекст в цитатах (lb/la) |
| `selectedScript` | письменность пали |
| `removePunct` | убирать пунктуацию |
| `uiScale` | размер текста |
| `theme`, `themeButtonAction`, `lightMode`, `darkSwitch` | тема (пишутся все четыре — так делает `themeswitch.js`) |
| `selectedDict`, `dictionaryVisible`, `multiSelectMode`, `dictAutoLookupDelay` | словарь |
| `localSearchHistory` | история поиска (пары `[текст, url]`) |
| `dgReadMarks:<запрос>\|<область>` | отметки «прочитано» в выдаче, отдельно на каждый поиск |
| `dg_suttaProgress`, `dg_cloudProgress`, `dg_progressEnabled`, `dg_autoJumpProgress` | прогресс чтения |

Важное для SPA: **страницы читают эти ключи при инициализации**. Настройки меняются в другом
документе (`/settings/`), поэтому там, где нужна реакция на лету, уже стоят слушатели `storage`
(тема на странице поиска, язык/письменность/словарь в кадре образца). В SPA настройки, скорее
всего, окажутся в том же документе — событие `storage` в своём же окне НЕ приходит, и эти места
придётся переводить на прямой вызов.

## 6. Прод и легаси: чего нельзя трогать

Старый PHP-проект (`dhammagift/dg`) на проде лежит в `/var/www/html`, dg-node — в его подпапке
`nodejs`. Общие ассеты подключены симлинками, `siteroot/*` — это они. Правило: **прод не трогаем**.

Если общий файл надо поправить — кладём патченую копию в `public/overrides/...`, она отдаётся
раньше (см. маунты в `dg-light.js`). Так уже сделано с `read/js/voice.js`, `js/settings.js`,
`js/search-render.js`, `js/smoothScroll.js`, `js/dg-text-router.js`, `js/paliLookup.js` и
`js/autopali.js`. В шапке override-копии стоит пометка, чем именно она отличается от легаси.

Локальная особенность Windows: часть симлинков в `siteroot/` не разворачивается
(`core.symlinks=false`), файлы отдают 404. Лечится копией из `C:\soft\dg\...` или junction'ом;
в git это не коммитим, `siteroot/*` всегда висят как ` D` в `git status` — **никогда не делайте
`git add -A`**.
