# Офлайн-база: одним сжатым файлом (передача, 2026-09-12)

Раздаём не урезанную копию корпуса, а **полную базу, сжатую в один файл**: человек скачивает,
распаковывается, всё готово. Без сборки индексов на устройстве, как это делают другие
приложения (там после скачивания ещё полчаса что-то строится).

## Как собирается

```
node publish-offline-db.js [--source=dg.db] [--out=siteroot/mobile-data]
```

База **одна**: `dg.db`, та самая, с которой работает сайт. Таблица `meta` пишется при её
сборке (`build-search-db.js`, функция `writeMeta`), а не дописывается потом во временную копию —
поэтому публикация ничего не меняет, только читает `build_id`, сжимает файл и пишет манифест.

`meta` обязательна: `public/offline/db-worker.js` после распаковки читает `SELECT key, value
FROM meta` и сверяет `build_id` с именем, под которым сохранил файл. База без этих строк
отвергается как незавершённое скачивание — то есть 216 МБ впустую. Если `meta` нет, публикация
останавливается и просит пересобрать базу. Непустой `dg.db-wal` рядом — тоже остановка: часть
данных ещё не в самом файле.

В манифесте объявлен **только** `file_gz`: когда объявлены оба, клиент предпочитает несжатый
файл (его можно докачать после обрыва). Здесь выбран вес.

## Что уже сделано

- Артефакт собран, проверен и **выложен на прод** (`/var/www/html/nodejs/siteroot/mobile-data/`):
  `dg.db.gz` 216 МБ + `db-manifest.json`, build `1a6acd81ec3df8d2`.
- Проверено: после распаковки sha256 сходится с манифестом, `meta` на месте, 7605 сутт, FTS
  ищет (kacchapa — 42 совпадения), 24 языка переводов вместо прежних двух.
- Прод отдаёт манифест с `file_gz` и держит `Range` на архиве (206).
- Копия артефакта осталась в `/root/offline-publish/` — на случай отката.

Замеры: 595 МБ → 216 МБ (2.8x, 45–80 с на сборку). Против прежних 509 МБ несжатой урезанной
базы это вдвое меньше трафика и все языки вместо двух.

## Что осталось

1. **Проверить на живом устройстве**: скачивание, распаковка, поиск. В headless-браузере
   проверить нельзя — см. п.2.
2. **Запись в OPFS не проверяется.** Скачивание падает с `SQLITE_CORRUPT`, когда браузер даёт
   мало места: байты приходят все до одного, но записи под конец молча не проходят, а
   `importDb` их не сверяет. Воспроизводится ОДИНАКОВО на сжатой и на прежней несжатой базе —
   к сжатию отношения не имеет. `storagePlanFor()` считает запас 1.15× и пропускает, хотя по
   факту не влезает. Чинить: сверять записанное и/или считать запас честнее.
3. **Докачка сжатого.** Сейчас её нет, и не из-за HTTP (`Range` на `.gz` работает, сервер
   отдаёт 206), а потому что воркер распаковывает на лету: в промежуточном файле лежат
   распакованные байты, на проводе — сжатые (`db-worker.js`: `const have = (gzip || !scratch) ?
   0 : ...`). Варианты: хранить сжатые байты и распаковывать в конце (на устройстве нужно 811 МБ
   вместо 595) либо архив из независимых gzip-блоков со смещениями в манифесте (~80 строк,
   лишнего места не требует). Второе лучше.
4. **Убрать `dg-mobile.db`** (509 МБ) после подтверждения на устройстве. Диск на 91 %.
5. **Снести `build-mobile-db.js`** — сайту он больше не нужен; приложение (`dg-app-full`) на
   него ссылается, сначала согласовать.
6. **Ревью офлайн-слоя**: `public/offline/{db-worker,app,offline-status}.js`,
   `public/service-worker.js`, `publish-offline-db.js`, раздача `/mobile-data` в
   `dg-fastify.js`. Там уже нашлись два протухших утверждения: «gzip для этой базы — проигрыш,
   168→177 МБ» (сегодня 595→216) и абзац про отключённое сжатие, где не сказано, что речь о
   сжатии на лету, а не вообще.
