## Суть решения (уже принята по существу)

**Питоновский стек `dg-mcp` не форкаем.** MCP — это плагин к `dg-fastify.js` поверх уже
готовой `dg.db`, плюс stdio-энтрипоинт для локального использования и для офлайн-приложения.

Причина: единственное, ради чего имело смысл брать чужой стек — слой данных
(PostgreSQL + pgvector + индексы). После перехода на `dg.db` он у нас свой, лучше
приспособленный под наши языки, и второй стек означал бы вторую копию тех же данных,
второй язык в обслуживании и — главное — **два разных поиска по одному корпусу**,
которые расходятся в выдаче на одном и том же запросе.

## На чём это основано

Состояние на момент написания — `dg-node` ветка `indep`, коммит `25a6888`:

- `dg.db` строится `build-search-db.js`, читается `dg-fastify.js` через встроенный
  `node:sqlite` (`DatabaseSync`, `{ readOnly: true }`) — нативных npm-зависимостей у БД нет.
- Схема: `suttas(id, category, dir_path, title, mr)`,
  `texts(sutta_id, segment_id, ord, kind, lang, translator, source, txt)` (~1.4 млн строк),
  `html(...)`, `fts` — FTS5 с `content='texts'`, `tokenize='trigram remove_diacritics 1'`.
- `kind` ∈ `root` | `variant` | `translation`; `ord` — позиция сегмента в файле, ею
  воспроизводится контекст `grep -B/-A`.
- В индексируемую копию вшит ё-фолдинг (внешний контент — поэтому `rebuild` делать нельзя).
- AI-переводы хранятся, но в FTS не попадают (решение владельца: скрытый контент).
  `dn84` исключён как усечённый дубль `dn16`.
- `/search?q=dukkha`: было ~42 с (grep + перечитывание JSON), стало **~0.1 с**.
- Мобильное приложение приводится к той же схеме, что и сайт (решение владельца,
  2026-09-05) — значит один корпус и одна семантика поиска на всех трёх поверхностях:
  веб, приложение, MCP.

Схема `texts` ложится на MCP-инструменты почти один в один: `kind` + `lang` + `translator`
— это готовое сравнение переводов, `ord` — окно контекста вокруг попадания, `segment_id` —
якорь для ссылки на наш ридер.

## Что MCP даёт

- **Русская Типитака для AI-агентов.** Ни один публичный MCP-сервер сегодня этого не даёт:
  у `tripitaka-mcp` жёстко пали / тайский / английский, русского нет ни в схеме, ни в модели.
  Наши `ru_o`, `ru_sv`, `ru_other` — то, чего больше нет ни у кого.
- **Ссылка на наш ридер в каждом ответе** (`cross_reference` с якорем на сегмент): и
  верификация цитаты пользователем, и трафик.
- **Офлайн-стек целиком.** Тот же MCP как stdio-сервер внутри APK: локальная модель +
  наш канон, ничего не уходит с устройства.
- **Каналы распространения:** Claude Desktop / Claude Code, Cursor, коннекторы ChatGPT,
  каталоги MCP (glama.ai, smithery.ai, официальный реестр).

## Инструменты

Первая очередь — всё поверх `dg.db` напрямую, не через HTTP-эндпоинты:

| Инструмент | Что делает |
|---|---|
| `search_suttas` | поиск по пали + ru + en, сегменты со ссылками на ридер |
| `get_sutta` | сутта целиком / оглавлением / окном вокруг сегмента (`ord`) |
| `compare_translations` | один сегмент во всех переводах (`translator`) |
| `list_structure` | структура канона и покрытие по языкам |

Вторая очередь — порт из `dg-mcp`, инфраструктуры не требует:

| Инструмент | Что делает |
|---|---|
| `verify_quote` | есть ли цитата реально в каноне (в т.ч. через границу сегментов) |
| `define_from_suttas` | канонические формулы определения («Katamañca X? … ayaṁ vuccati X», виная «X nāma») |
| `get_word_definition` | словарь (нужны данные — `dictPlugin` / DPD) |
| `parse_pali_word` | отсечение палийских окончаний (`bhikkhūnaṁ` → `bhikkhu`) |

## Что берём из `dg-mcp`, а что нет

**Берём** (содержимое и текст, не инфраструктуру):

- описания инструментов и server instructions (`main.py`, ~строки 90–300) — именно они
  заставляют модель выбрать правильный инструмент и вставить ссылку на ридер в ответ;
  переписать под наши эндпоинты и наш домен, но структуру брать их;
- `sutta_definitions.py` (736 строк) — распознавание канонических формул, чистая логика
  над текстом, портируется в JS почти дословно;
- `sutta_verify.py` — логика `verify_quote`;
- `parse_pali_word` — таблица палийских окончаний;
- `infra/Caddyfile` — rate limit (10 запросов / 10 с и 60 / мин на IP);
- `topics/*.md` — справочные страницы, чтобы агент не делал 30 вызовов подряд;
- `skills/tipitaka-research.md` — как образец research-workflow.

**Не берём:** PostgreSQL, pgvector, `sentence-transformers`, Docker-стек, их загрузчики
данных, их ридер, их сборку SQLite. Всё это у нас уже есть в своём виде.

## Блокеры — снять до публичного запуска

1. **Ранжирования нет.** Триграммный токенизатор выбран сознательно (чтобы `kacchapa`
   находил `mahākacchapa`, как делал grep), но bm25 поверх триграмм как мера релевантности
   бессмысленна и в коде не используется. Человек видит всю таблицу и выбирает глазами;
   агент берёт первые 5 и на них отвечает. Нужен явный порядок — и почти всё для него
   уже считается в обогащении: число попаданий в сутте, попало ли в пали-`root` или только
   в перевод, плюс `mr`.
2. **Regex-ветка — дыра под публичный эндпоинт.** `REGEX_METACHARS` в запросе переключает
   поиск на `SQL_SCAN`: полный проход по ~1.4 млн строк с JS-регэкспом внутри SQLite,
   ~5 с CPU на запрос. Для нашего UI нормально — так ходят единицы. Для открытого MCP это
   ручка, которой сервер кладут парой параллельных запросов, и rate limit по IP тут не
   спасёт. В MCP-инструменте regex либо не выставлять параметром вообще, либо отдельный
   жёсткий лимит.
3. **Минимальная длина запроса.** У триграммного токенизатора жёсткий пол в 3 символа
   (`MIN_KEYWORD_LENGTH` его уже держит). Это должно быть написано в описании инструмента,
   иначе агент будет молча получать пустоту на коротких запросах.

## Ресурсы

**Разработка:**

| Этап | Оценка |
|---|---|
| MCP-плагин (`/mcp` в `dg-fastify.js` + stdio) и 4 инструмента первой очереди | 2–4 дня |
| Ранжирование + защита regex-ветки (блокеры 1–2) | 1–2 дня |
| `verify_quote` + `define_from_suttas` | 3–5 дней |
| Словарь + `parse_pali_word` | 2–3 дня |

Минимум для публичного запуска — первые две строки: **3–6 дней**.

**Прод:** тот же процесс, тот же VPS, новых сервисов нет. Из зависимостей — только
`@modelcontextprotocol/sdk`. Память +50–100 МБ, ~0.1 с CPU на вызов (regex-ветка — см.
блокер 2). **Дополнительных затрат на инфраструктуру нет.** Добавить rate limit.

Оговорка про цифры из `docs/CAPACITY.md` в `dg-mcp` (2 vCPU / 4 ГБ ≈ $24/мес →
200–500 пользователей в день): они сняты с их стека, где на каждый запрос работает
CPU-инференс модели эмбеддингов. У нас этого нет, наш профиль нагрузки легче — их числа
можно брать как консервативную нижнюю границу, не как прогноз.

**Семантический поиск — отдельный, необязательный этап.** `node:sqlite` умеет
`loadExtension` (через `allowExtension: true` при открытии + `enableLoadExtension`), так что
`sqlite-vec` достижим без Python и без Postgres — но отдельным соединением: текущее открыто
read-only без этого флага. Стоимость: эмбеддинги корпуса считаются один раз на сборке,
в рантайме эмбеддится только запрос (`transformers.js` / `onnxruntime-node`, модель в ONNX
~50–90 МБ квантованная). Объём векторов: 384 измерения × float32 — порядка +650 МБ на
корпус, в int8 ~170 МБ, в бинарном виде ~21 МБ. На сервере приемлемо, в APK — только
квантованный вариант. Решать до того, как считать эмбеддинги, а не после.

## Лицензия

Код `tripitaka-mcp` — MIT, форкать и переиспользовать можно. Данные разные: словарь
Payutto — **только некоммерческое использование, контент менять нельзя**. Dhamma.gift —
дана, не коммерция, так что подходит. Но если публикуем свой дамп или APK со словарём
внутри — тащим `NOTICE.md` вместе с ним.

  в политике).
