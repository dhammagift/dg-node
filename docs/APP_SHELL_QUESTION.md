# Вопрос для обсуждения: оболочка нативных приложений (Android + iOS) поверх существующего сайта

Документ для форума/других ИИ. Ниже — только факты о проекте и конкретные вопросы; готового
решения у нас нет.

## Что уже есть

- Сайт: Node (Fastify) + SPA на ванильном JS. UI — `search/index.html`, `public/overrides/*`,
  `public/spa/*`, `reader/*`; сборка статики из одного репозитория.
- Данные: SQLite ~480 МБ (корпус пали + переводы ru/en, FTS5 с `tokenize='trigram'`). Те же
  ответы обязаны приходить из трёх источников (grep-легаси, `dg.db` на сервере, локальная база
  клиента) — это проверяется тестами паритета JSON.
- Ядро поиска/ридера: `core/search-core.js` (чистый JS, работает поверх handle SQLite) отвечает
  на `/search`, `/api/text/:id`, `/api/nav/:id`, `/api/toc*`.
- Веб-офлайн: service worker + Web Worker + `@sqlite.org/sqlite-wasm` + OPFS-SAH pool. База
  скачивается по кнопке (480 МБ, Range-докачка), лежит в OPFS, словарь DPD (24 МБ) — в кеше SW.
  Это работает и в PWA, и в TWA (TWA = Chrome, поэтому делят одно хранилище с вкладками).
- Приложение на Capacitor (`dg-app-full`) существовало раньше: тот же UI, но данные из нативного
  SQLite-плагина. Сейчас это «старый» вариант, новый нужен с нуля.

## Что нужно

1. Нативные приложения **Android и iOS**, которые:
   - рисуют **тот же UI сайта** (никакого второго фронтенда, поддержки дизайна в приложении нет);
   - при первом открытии **по умолчанию скачивают базу** (прогресс, отмена, докачка);
   - хранят базу **вне браузерного хранилища** — файлом в песочнице приложения;
   - нативно поддерживают только шорткаты и share (и, вероятно, импорт/экспорт файла базы).
2. Один источник правды по запросам: не хочется портировать SQL на Kotlin и Swift и потом
   ловить расхождения — идентичность ответов проверяется тестами, но дублирование кода дорого.

## Что из этого следует для выбора оболочки (аргументы в пользу Capacitor)

TWA (Chrome под капотом) закрывает только «онлайн-приложение». Всё, что нужно сверх веб-платформы,
требует нативного кода, и это аргументы в пользу Capacitor (или своей оболочки на
WebView/WKWebView):

1. **Хранилище базы вне браузера.** 509 МБ файлом в песочнице приложения: без квоты, без
   вытеснения, без `createSyncAccessHandle` и без гонки, из-за которой мы уже ловили
   `SQLITE_CORRUPT` в браузере. У TWA это невозможно — там OPFS Chrome.
2. **Динамические шорткаты из истории.** В PWA/TWA шорткаты статические (манифест): телефон
   показывает первые 3–4, и подставить «последние прочитанные» нельзя — доступа к Android
   `ShortcutManager` у Chrome нет, у iOS для веб-приложения на домашнем экране шорткатов нет
   вообще. В Capacitor: страница читает свою историю (`localSearchHistory`, `dg_favorites`,
   `visitCount`) и отдаёт список в свой плагин — `ShortcutManager` (Android) и
   `UIApplication.shortcutItems` (iOS). Нативная сторона localStorage сама не видит, значит нужен
   ровно один маленький плагин-мост.
3. **Фоновая докачка базы** (WorkManager / URLSession) и уведомление о прогрессе — вместо «не
   закрывайте вкладку», как в PWA.
4. **Sharing и импорт/экспорт файла базы** — нативные API в любом случае.
5. **UI при этом остаётся сайтовым.** Никакого второго фронтенда: сборочный приём из
   `dg-app-full` (`build-page.js` + `build-assets.js`, `DG_NODE_REF`) генерирует тот же билд, а
   нативного кода — пять пунктов выше, каждый в виде отдельного плагина.

## Варианты, которые мы видим

- **A. Capacitor + нативный SQLite-плагин**, приложение отвечает на `/search`, `/api/text`,
  `/api/nav` через мост. Плюс: быстро, плагины (SQLite/Filesystem/Share/App) есть. Минус: запросы
  придётся реализовать нативно (или гонять SQL через мост), асинхронный API плагина.
- **B. Своя оболочка:** Kotlin + `android.webkit.WebView`, Swift + `WKWebView`, свой мост и свой
  SQLite. Плюс: полный контроль, никакого фреймворка. Минус: всё руками (мост, загрузчик,
  обновления, разрешения).
- **C. WebView + `sqlite-wasm` + VFS поверх нативного файла.** Плюс: JS-ядро остаётся единственным
  (`core/search-core.js`). Минус: нужен **синхронный** доступ к файлу из wasm — либо
  `Atomics.wait` + SharedArrayBuffer (нужны COOP/COEP-заголовки и worker), либо патч VFS.

## Вопросы

1. Что в 2026 разумнее для «тонкой оболочки поверх существующего веб-UI»: Capacitor или
   собственная оболочка на WebView/WKWebView? Где больше подводных камней на практике?
2. Как на практике дать JS **синхронный** доступ к SQLite в WebView (вариант C) — есть ли готовые
   VFS/плагины с синхронным мостом, или это всегда SAB + `Atomics.wait` + отдельный поток?
   Насколько это стабильно на iOS (WKWebView) сейчас?
3. Если идти путём A: чем портировать запросы, чтобы не разъехаться с JS-ядром — общий SQL-слой,
   генерация из одного описания, или всё же вариант C?
4. База 480 МБ: класть в APK/IPA или скачивать при первом запуске? Что с App Store/Google Play
   (лимиты размера, «downloaded content»)? Для обновлений у нас уже есть таблица `chunks`
   (hash на sutta/kind/lang/translator) — есть ли смысл в дельта-обновлениях, или проще
   перекачивать файл целиком?
5. iOS: какие подводные камни у WKWebView с локальным UI (file://, custom scheme, service worker
   отсутствует), фоновой докачкой (URLSession) и хранением 480 МБ (iCloud-бэкап, «не бэкапить»)?
6. Что из перечисленного вы бы **не** делали и почему?
7. Если выбирать Capacitor ради пунктов 1–4: какие плагины брать готовыми, а какие писать самим
   (шорткаты, фоновая докачка), и нет ли для динамических шорткатов готового плагина, который мы
   не нашли?
