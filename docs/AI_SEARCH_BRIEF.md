# AI-поиск — как это работает

Обновлено 2026-09-13, описывает реально построенное (изначально это был бриф для дизайнера
до реализации — та версия сохранена в истории git, если нужно посмотреть исходный план).

## Контекст

Обычный поиск точный (grep/FTS по палийскому тексту и переводам). Если пользователь
описывает сутту своими словами ("притча про слепую черепаху") или ошибается в
транслитерации — точный поиск даёт 0 результатов.

## Когда включается

Два пути:

1. **Автоматический фолбэк** — точный поиск дал 0 результатов (и запрос не "слишком короткий"),
   `search/index.html` сам вызывает `window.dgRunAiSearch(keyword, scope)`.
2. **Вручную** — кнопка «AI mode» в тулбаре результатов (`#btn-ai-mode`, `search/index.html`
   `#dg-toolbar-buttons`): прогоняет ТЕКУЩИЙ запрос через ИИ-поиск в любой момент, даже если
   точный поиск уже что-то нашёл. Разовое действие, ничего не запоминает — персистентных
   режимов (zero/always/off из ранней версии плана, `docs/AI_MODE_DESIGN.md`) нет.

## Пайплайн (`dg-fastify.js` → `/api/ai-search`)

Порядок важен — каждый шаг придуман, чтобы не звать LLM без нужды:

1. **Одно слово (без пробелов)** — сначала проверяем DPD напрямую (`core/dpd-lookup.js`),
   без единого обращения к LLM:
   - слово реально существует в DPD → ищем по смыслу через search_hybrid, используя
     собственную глоссу DPD (не догадку модели); плюс это же слово как "предполагаемое".
   - слова нет, но DPD нашла похожие формы ("closest matches") → эти формы и показываем
     как «может быть, вы искали» (после проверки через ту же DPD, что они существуют) —
     это путь "только слова", таблица сутт не строится.
   - слова нет и похожих форм тоже нет — честно ничего не найдено, **LLM вообще не
     вызывается** (раньше на этом месте модель выдумывала типовую заглушку вроде
     "dhamma, sacca, anicca, dukkha, nibbana" на любой непонятный ввод — от неё отказались).
   - DPD недоступна (сетевая ошибка после ретрая) — не падаем, идём дальше, в п.2.
2. **Многословный запрос** (или DPD была недоступна) — полный LLM-пайплайн,
   `core/ai-search.js` → `normalizeQuery()`:
   - форсированный tool-call `dispatch_search({recognized, english_query, pali_candidates})` —
     модель не может ответить свободным текстом, только этим вызовом.
   - `recognized: false` (клавиатурная бессмыслица типа "лфадмлот") — тоже ничего не ищем,
     сразу пустой ответ. Раньше модель была вынуждена что-то придумать и для мусорного
     ввода тоже, а `search_hybrid` потом реально находил что-то по этой придумке.
   - иначе — ищем через `search_hybrid(english_query + специфичные из pali_candidates)`.
     Кандидаты подмешиваются в сам поисковый запрос (тот же приём, что и в п.1 с глоссой
     DPD), но только "специфичные" — самые частотные, ничего не говорящие термины
     (dhamma, sutta, sacca, anicca, dukkha, anatta, nibbāna, kamma, magga, metta —
     список в `GENERIC_PALI_TERMS`, `dg-fastify.js`) отфильтрованы: они всегда "правильные"
     по словарю, но не сужают поиск ни капли, только шумят.
   - эти же LLM-угаданные кандидаты **не показываются как чипы «может быть, вы искали»** —
     слишком ненадёжны для этого; чипы — только из настоящих подсказок DPD (п.1) или
     нечёткого поиска по словоформам корпуса (see `metadata.suggestions`,
     `core/search-core.js` — параллельная фича, не LLM).
3. Кэш ответа 10 минут в памяти (ключ: язык + область поиска + запрос).

## Что показывает страница

**Не отдельная вёрстка карточек**, как задумывалось в первой версии плана — сутты уходят
в ТУ ЖЕ самую таблицу, что и обычный поиск (`#pali`, `window.DgSearchRender.buildDataTable`,
`public/overrides/js/ai-search.js`). Настоящие DataTables-треугольники, разворачивание строк,
кнопка "свернуть всё" (Saṁvaṭṭo/Vivaṭṭo) — всё бесплатно, потому что это буквально тот же
компонент, не имитация.

Слова-кандидаты — чипы (`#ai-words`): клик по самому слову открывает словарь (тот же
`handleWordLookup`, что у любого палийского слова на странице, с настройкой пользователя —
попап/новое окно/полная страница); маленькая иконка рядом — подставляет слово в поле поиска,
ничего не запуская сама.

## Четыре исхода

| Исход | Что видно | Языковая пилюля Pāli/перевод | raw data |
|---|---|---|---|
| Только слова (опечатка) | чипы, без таблицы | да | да |
| Полный ответ | настоящая таблица | да | да, в футере таблицы |
| Ничего не найдено | текст, без кнопок | нет | да |
| Ошибка (ИИ недоступен/сеть) | текст + «к точному поиску» | нет | да |

`raw data` — маленькая ссылка внизу каждого исхода, разворачивает панель с тремя полями
(инпут / кандидаты / нормализованный запрос), у каждого своя кнопка Copy
(`execCommand('copy')` — на сервере без HTTPS `navigator.clipboard` недоступен).
Сервер также пишет одну строку в лог (`pm2 logs`) на каждый вызов `/api/ai-search` —
не нужно просить скриншот, чтобы посмотреть, что реально ушло в поиск.

## Языки

Запрос может быть на любом языке — LLM сам переводит на английский для семантического
поиска. UI-тексты (заголовки состояний, подписи) — на языке интерфейса (ru/en).

## Обязательно как и весь остальной UI проекта

- Мобильная и десктопная версия
- Светлая и тёмная тема
- Стиль/шрифты/отступы — общий визуальный язык поиска и ридера

## Известные ограничения

- Качество семантического поиска зависит от того, насколько специфичен переведённый
  запрос — короткое описание без ключевых слов (например, притча пересказана без слова
  "пыль", хотя в оригинале речь о пыли на ногте) может не найтись, даже если корпус
  содержит нужную сутту. Подмешивание кандидатов (см. выше) частично компенсирует это,
  но не всегда.
- Персистентные режимы zero/always/off (см. `docs/AI_MODE_DESIGN.md`) не реализованы —
  только разовая ручная кнопка.
