# AI-поиск — бриф для дизайнера

## Контекст

Сейчас поиск точный (grep/FTS по палийскому тексту и переводам). Если пользователь
описывает сутту своими словами ("притча про слепую черепаху") или ошибается в
транслитерации — точный поиск даёт 0 результатов, и человек упирается в пустой
экран.

## Когда включается

AI-режим — **не отдельная кнопка, а автоматический фолбэк**:

1. Пользователь вводит запрос как обычно, жмёт "искать".
2. Точный поиск отрабатывает как сейчас.
3. Если результатов **0** — вместо пустого экрана показывается AI-режим:
   тот же запрос уходит на семантический поиск + подбор палийских слов.
4. Если точный поиск что-то нашёл — AI не включается вообще, пользователь
   видит обычную таблицу результатов, как сейчас.

Т.е. с точки зрения пользователя это одна кнопка "искать" — просто иногда после
неё показывается другая страница.

## Что показывает страница AI-режима

Не таблица результатов (DataTables) — нужен другой макет. Два независимых блока:

### Блок 1 — сутты, которые (возможно) имел в виду пользователь

Список карточек, не строк таблицы. На карточку:
- Название сутты (пали + перевод), номер (dn22, mn129...)
- Короткая цитата/фрагмент — именно то место, из-за которого сутта попала в
  выдачу (не первый абзац сутты, а релевантный сегмент)
- Явная пометка неточности результата — это не "нашли точное совпадение", а
  "предполагаем, что вы искали". Нужна визуальная разница с обычной таблицей
  точных результатов, чтобы не спутать уверенность с гарантией
- Клик по карточке → открывает сутту в обычном ридере, сразу на нужном
  сегменте (URL-паттерн `/dn22:2.2` уже есть, просто нужный сегмент из ответа)

Ожидаемое количество карточек: 3-5, не 20.

### Блок 2 — предполагаемые слова для точного поиска

Отдельно от карточек сутт — короткий список слов-кандидатов (палийские термины,
реально существующие в словаре, не выдуманные), которые могли иметь в виду.
Каждое слово — кликабельный чип/кнопка, клик по которому запускает обычный
точный поиск по этому слову (переключает пользователя обратно в привычный режим).

Это отдельная и самостоятельно полезная штука даже без блока 1 — например,
если человек ищет "страдание" по-русски, чипы могут предложить "dukkha".

### Состояния, которые нужно нарисовать

- **Загрузка** — в отличие от точного поиска (мгновенный), AI-режим ходит во
  внешний сервис + LLM, может занять 1-3 секунды. Нужен осмысленный
  промежуточный экран (skeleton/спиннер с текстом), не просто "зависшая"
  страница
- **Ничего не нашли и AI тоже** — редкий, но возможный случай (оба блока
  пустые). Нужен честный empty-state, не "0 результатов" как в обычном поиске
- **Ошибка/сервис недоступен** — внешний AI-сервис может быть недоступен;
  страница должна тихо деградировать (например в точный поиск с сообщением),
  не показывать пользователю техническую ошибку

### Путь назад

Пользователь должен легко вернуться к обычному точному поиску без AI-подсказок
(например если предположения совсем не в тему) — не тупик, а явная ссылка/кнопка
"искать точно как ввёл".

## Языки

Запрос может быть на любом языке (не только ru/en) — сайт уже поддерживает много
языков переводов. Дизайн не должен закладывать фиксированную длину текста под
конкретный язык (кириллица/латиница/палийская диакритика вперемешку, длины
сильно отличаются между языками) — так же, как остальной сайт уже это учитывает.

## Обязательно как и весь остальной UI проекта

- Мобильная и десктопная версия
- Светлая и тёмная тема
- Стиль/шрифты/отступы — в общем визуальном языке текущего поиска и ридера,
  это дополнительный режим существующей страницы, а не отдельный микросайт
